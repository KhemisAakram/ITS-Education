# ITS Education Progression Framework

## Purpose

This framework defines the capabilities a student should demonstrate when progressing through the ITS Education pathway.

Progression is based on **demonstrated capability**, not class count or age alone.

The framework connects:

**Competency → Project Evidence → Independence → Level Transition**

Detailed course assessments belong in the individual level/course chats. This document defines the institute-wide progression standard.

---

# 1. Independence scale

Every technical competency can be observed at four levels:

| Stage | Meaning |
|---|---|
| **Guided** | Student can perform the task with substantial teacher guidance. |
| **Developing** | Student can perform the task with limited support and prompting. |
| **Capable** | Student can perform the task independently in familiar situations. |
| **Independent Maker** | Student can apply the competency independently, debug problems, explain decisions and improve the result. |

The expected independence increases from Level 1 to Level 4.

---

# 2. Explorer → Maker

A student progressing from **Level 1 Explorer** toward **Level 2 Maker** should demonstrate the following.

## Electronics

The student can:

- Identify common basic components.
- Recognize LED polarity.
- Build simple low-voltage circuits from a diagram.
- Use switches and buttons.
- Use resistors appropriately in basic circuits.
- Connect simple buzzers, sensors and actuators.
- Explain the basic purpose of the components used.
- Follow laboratory safety procedures.

## Programming

The student can:

- Understand that a program is a sequence of instructions.
- Create simple programs.
- Use basic inputs and outputs.
- Use simple loops/repetition.
- Connect program behavior to a physical output.
- Make basic changes to an existing program.

## Sensors and actuators

The student can:

- Explain what a sensor does.
- Use a basic sensor in a project.
- Use LEDs, buzzers, motors and servos in guided projects.
- Observe how an input changes system behavior.

## Robotics

The student can:

- Assemble a simple mechanical system.
- Build a basic two-wheel robot.
- Connect basic motors and sensors.
- Explain the basic purpose of the robot's main parts.

## Engineering and debugging

The student can:

- Follow a build sequence.
- Observe a system when it does not work.
- Describe the visible problem.
- Try a simple change.
- Test whether the change helped.
- Improve a guided project.

## Documentation and communication

The student can:

- Make simple circuit sketches.
- Record observations.
- Record basic test results.
- Explain what was built.
- Explain the basic way the project works.

### Transition evidence

A student should have evidence across multiple projects showing that they can **build, test, explain and make simple improvements**, rather than only reproduce one memorized project.

# 3. Maker → Junior Engineer

A student progressing from **Level 2 Maker** toward **Level 3 Junior Engineer** should demonstrate the following.

## Electronics

The student can:

- Explain voltage, current and resistance at the level expected by the course.
- Use a multimeter for basic measurements.
- Build sensor-based circuits.
- Select common components for a defined purpose.
- Connect microcontrollers to sensors and actuators.
- Understand basic motor-control and driver concepts.
- Troubleshoot common circuit problems.

## Programming

The student can:

- Program a microcontroller using structured code.
- Use variables.
- Use conditions.
- Use loops.
- Use functions.
- Read inputs and control outputs.
- Combine several inputs and outputs in one system.
- Modify and debug programs.

## Sensors and actuators

The student can:

- Select an appropriate sensor for a defined task.
- Read sensor data.
- Control motors and servos.
- Combine sensors and actuators into a functioning system.
- Explain the relationship between input, processing and output.

## Robotics

The student can:

- Build a functional robot.
- Integrate motors, sensors and programming.
- Implement programmed robot behavior.
- Troubleshoot mechanical, electrical and software problems.
- Make design modifications based on testing.

## Engineering

The student can:

- Translate a defined problem into a technical solution.
- Plan a prototype.
- Choose components within defined constraints.
- Test a prototype.
- Compare expected and actual behavior.
- Modify the design based on evidence.

## Debugging

The student can use a repeatable process:

**Observe → Describe → Hypothesize → Test → Identify → Correct → Test again**

The student should increasingly isolate problems instead of changing several things at once.

## Documentation and communication

The student can:

- Produce circuit/system diagrams.
- Record measurements.
- Record debugging steps.
- Explain system behavior.
- Document project changes.
- Present a working project and explain how it works.

### Transition evidence

A student should demonstrate that they can **build, measure, program, troubleshoot, document and modify** a system with decreasing teacher assistance.

---

# 4. Junior Engineer → Young Engineer

A student progressing from **Level 3 Junior Engineer** toward **Level 4 Young Engineer** should demonstrate the following.

## Electronics

The student can:

- Analyze more complex electronic subsystems.
- Select components based on system requirements.
- Work with analog and digital signals at the course level.
- Integrate sensors, drivers and actuators.
- Work with power and motor-control systems.
- Prototype and debug electronic subsystems.
- Begin working with PCB-oriented design.

## Programming

The student can:

- Program in C/C++ at the required level.
- Use Python for appropriate engineering tasks.
- Structure larger programs.
- Communicate between software and hardware.
- Work with ESP32-class systems.
- Use communication interfaces/protocols introduced by the curriculum.
- Debug hardware/software interaction.

## Robotics and control

The student can:

- Design robot subsystems.
- Integrate mechanical, electronic and software components.
- Use sensor information to control behavior.
- Develop increasingly autonomous systems.
- Understand basic control concepts.
- Test robot performance and modify the design.

## Engineering design

The student can:

- Define requirements.
- Identify constraints.
- Develop a system architecture.
- Select technologies and components.
- Create a prototype.
- Define tests.
- Analyze results.
- Iterate from evidence.
- Document engineering decisions.

## CAD and mechanical design

The student can:

- Create basic mechanical designs in CAD.
- Design parts for fabrication/prototyping.
- Integrate mechanical elements with electronics.
- Modify mechanical designs after testing.

## Documentation and communication

The student can:

- Produce technical diagrams.
- Document design decisions.
- Record test procedures and results.
- Explain limitations.
- Present technical decisions and justify them using evidence.

### Transition evidence

A student should demonstrate that they can **define, design, prototype, integrate, test, debug and document a complete system** with substantially reduced teacher direction.

# 5. Young Engineer completion standard

The Level 4 endpoint represents the ability to undertake an independent engineering project.

A student completing the Young Engineer pathway should be able to:

1. **Define requirements**
   - Identify the problem.
   - Define desired system behavior.
   - Identify constraints.

2. **Develop system architecture**
   - Divide the problem into subsystems.
   - Define relationships between mechanical, electronic and software elements.

3. **Select components and technologies**
   - Choose components appropriate to requirements.
   - Explain relevant design decisions.

4. **Design electronics**
   - Develop and integrate electronic subsystems.
   - Consider power, interfaces and system requirements.

5. **Develop software**
   - Program the required embedded/system behavior.
   - Integrate software with hardware.

6. **Prototype mechanical elements**
   - Develop and test mechanical structures or mechanisms.
   - Use CAD/fabrication methods appropriate to the project.

7. **Integrate the system**
   - Combine subsystems into a functioning prototype.

8. **Test**
   - Define and perform meaningful tests.
   - Record evidence.

9. **Debug**
   - Isolate faults.
   - Identify likely causes.
   - Test hypotheses.
   - Correct and verify.

10. **Revise**
    - Use test evidence to improve the design.

11. **Document**
    - Record architecture, design decisions, tests, problems and revisions.

12. **Present**
    - Demonstrate the working system.
    - Explain the design.
    - Defend design decisions using evidence.
    - Identify limitations and possible improvements.

# 6. Competency domains

Progression should be tracked across the following institute-wide domains:

| Domain | Level 1 focus | Level 2 focus | Level 3 focus | Level 4 focus |
|---|---|---|---|---|
| Electronics | Basic circuits | Measurement and microcontroller systems | System electronics | Advanced/system electronics |
| Programming | Basic programming concepts | Microcontroller programming | C/C++, Python, ESP32 | Embedded/system programming |
| Sensors | Basic sensor use | Sensor integration | Sensor systems | Advanced sensing/integration |
| Actuators | LEDs, buzzers, motors, servos | Motor/servo control | Integrated actuation | Advanced control/integration |
| Robotics | Simple robot | Functional robot systems | Designed robotic systems | Advanced robotic systems |
| Engineering | Build and improve | Prototype and modify | Design systems | Engineer products/systems |
| Debugging | Basic fault finding | Systematic troubleshooting | Hardware/software diagnosis | System-level fault isolation |
| Documentation | Basic notebook | Test/debug records | Engineering documentation | Technical/product documentation |
| Communication | Explain project | Explain system | Explain design | Present and defend engineering decisions |
| Independence | Guided | Developing | Capable | Independent Maker |

---

# 7. Evidence required for progression

Progression decisions should use multiple forms of evidence:

- Completed projects
- Working prototypes
- Student engineering notebook
- Circuit/system diagrams
- Programming work
- Test results
- Debugging records
- Improvement iterations
- Teacher observations
- Student explanations
- Final project evidence
- Demonstrated independence

A single successful project should not, by itself, establish mastery.

---

# 8. Progression decision

A level transition should consider four questions:

### Technical capability
**Can the student perform the required technical tasks?**

### Engineering capability
**Can the student use testing and evidence to improve a system?**

### Independence
**How much teacher support is required?**

### Communication
**Can the student explain what they built, how it works, what went wrong, and what they changed?**

The student should demonstrate an appropriate level across the relevant competency domains before progressing.

---

# 9. Progression architecture

The complete progression is:

**Level 1 — Explorer**

Build → Experiment → Observe → Explain → Improve

↓

**Level 2 — Maker**

Build → Measure → Program → Debug → Modify → Explain

↓

**Level 3 — Junior Engineer**

Define → Design → Prototype → Integrate → Test → Debug → Document

↓

**Level 4 — Young Engineer**

Specify → Architect → Engineer → Integrate → Validate → Iterate → Present

---

# 10. Institute rule

The purpose of progression is not to move students through increasingly difficult content as quickly as possible.

The purpose is to increase:

**technical capability + engineering thinking + independence + evidence-based problem solving**

while maintaining the ITS Education learning cycle:

**Learn → Experiment → Build → Break → Debug → Understand → Improve → Create**
