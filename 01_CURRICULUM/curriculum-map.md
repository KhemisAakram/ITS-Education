# ITS Education Master Curriculum Map

## Purpose

This document is the master curriculum architecture for ITS Education.

It defines how the institute develops students from **Explorer → Maker → Junior Engineer → Young Engineer** across Programming, Electronics, Robotics, Engineering, Projects, and transferable competencies.

Detailed course design belongs in the individual Level 1–4 course chats. This document defines the progression that those courses must follow.

---

## 1. Institute progression

| Level | Age | Student identity | Core capability |
|---|---:|---|---|
| Level 1 | 6–8 | Explorer | I can make something happen. |
| Level 2 | 8–11 | Maker | I understand how the things I build work. |
| Level 3 | 11–14 | Junior Engineer | I can design a system. |
| Level 4 | 14–17 | Young Engineer | I can design and build a real product. |

Age is a guide. Progression should increasingly depend on demonstrated competencies, project evidence, independence, and assessment.

---

## 2. Master learning progression

**Discover → Build → Program → Understand → Design → Create**

The learning cycle used across the institute is:

**Learn → Experiment → Build → Break → Debug → Understand → Improve → Create**

The amount of teacher guidance decreases as student independence increases.

| Dimension | Level 1 | Level 2 | Level 3 | Level 4 |
|---|---|---|---|---|
| Learning mode | Guided discovery | Guided making | Engineering design | Product/system development |
| Main question | “What happens?” | “How does it work?” | “How should I design it?” | “How can I build a reliable solution?” |
| Guidance | High | Medium | Reduced | Low / mentoring |
| Projects | Highly guided | Structured with choices | Open-ended engineering | Open-ended product/system |
| Debugging | Observe and fix with support | Test and identify faults | Diagnose systematically | Diagnose at system level |
| Documentation | Basic project record | Engineering notebook habits | Engineering documentation | Technical/product documentation |
| Independence | Guided | Developing | Capable | Independent maker/engineer |

# 3. Subject progression

## Programming

| Level | Programming development |
|---|---|
| Level 1 | Scratch/programming concepts; sequences, inputs, outputs, loops; introductory microcontroller programming |
| Level 2 | Arduino programming; variables, conditions, loops, functions, inputs/outputs, sensors and actuators |
| Level 3 | C/C++, Python, structured programs, serial communication, ESP32, data and IoT foundations |
| Level 4 | Advanced C/C++, embedded programming, system architecture, communication, control software, integration |

### Programming progression

**Visual programming → Text programming → Structured programming → Embedded programming → System software**

---

## Electronics

| Level | Electronics development |
|---|---|
| Level 1 | Electricity, polarity, LEDs, resistors, switches, buttons, buzzers, sensors, motors, servos, basic microcontrollers |
| Level 2 | Circuit behavior, measurement, sensor systems, transistor/driver concepts, motor control, power basics, microcontroller interfaces |
| Level 3 | Analog/digital concepts, transistor and driver circuits, communication, power and motor control, circuit analysis, prototyping |
| Level 4 | Advanced electronics, power electronics, signal conditioning, PCB design, system power architecture, production-oriented electronics |

### Electronics progression

**Electricity → Circuits → Components → Sensors/Actuators → Microcontrollers → Power/control → PCB/system electronics**

---

## Robotics

| Level | Robotics development |
|---|---|
| Level 1 | Simple mechanisms, motors, servos, sensors, basic two-wheel robot |
| Level 2 | Robot construction, motor control, sensor integration, programmed behavior, mechanical mechanisms |
| Level 3 | Robot architecture, feedback/control foundations, autonomous behavior, mechanical design, CAD and system integration |
| Level 4 | Advanced robotics, control systems, autonomous systems, embedded software, sensing, mechanical/electronic integration |

### Robotics progression

**Mechanisms → Actuators → Sensors → Control → Autonomous behavior → Integrated robotic systems**

---

## Engineering

| Level | Engineering development |
|---|---|
| Level 1 | Build, test, observe, debug, improve |
| Level 2 | Measure, compare, modify, prototype and explain |
| Level 3 | Define requirements, design systems, prototype, test and document |
| Level 4 | Requirements, architecture, design, engineering trade-offs, prototype, validation, iteration and product/system development |

### Engineering progression

**Build → Measure → Debug → Prototype → Design → Document → Improve → Product**

---

# 4. Project progression

Projects are the main vehicle for applying knowledge.

| Level | Project character | Expected student behavior |
|---|---|---|
| Level 1 | Guided builds | Follow, experiment, explain and make small improvements |
| Level 2 | Structured builds with choices | Select methods/components and solve defined problems |
| Level 3 | Engineering challenges | Define parts of the solution, design, prototype and debug |
| Level 4 | Capstone/product projects | Define requirements, design architecture, build, validate and present a working system |

### Project guidance progression

**Recipe → Guided challenge → Design challenge → Open engineering project**

The project system should progressively reduce instructions and increase student decisions.

# 5. Competency progression

## Electronics competency

- **Level 1:** Identify basic components and build simple circuits safely.
- **Level 2:** Select and connect common components and measure basic circuit behavior.
- **Level 3:** Analyze, design and debug more complex electronic subsystems.
- **Level 4:** Design and integrate advanced electronic systems, including PCB-oriented work.

## Programming competency

- **Level 1:** Create simple programs and connect program behavior to physical outputs.
- **Level 2:** Write structured programs using inputs, outputs, conditions, loops and functions.
- **Level 3:** Develop multi-part programs and communicate with hardware and networked devices.
- **Level 4:** Develop embedded/system software and integrate software with complex hardware.

## Robotics competency

- **Level 1:** Build and control simple mechanisms and robots.
- **Level 2:** Combine motors, sensors and programming into functional robots.
- **Level 3:** Design robot subsystems and autonomous behaviors.
- **Level 4:** Integrate advanced sensing, control, mechanics and embedded software.

## Engineering competency

- **Level 1:** Build → test → debug → improve.
- **Level 2:** Measure → compare → modify → explain.
- **Level 3:** Define → design → prototype → test → document.
- **Level 4:** Specify → architect → engineer → validate → iterate → deliver.

## Debugging competency

- **Level 1:** Observe → describe → try a fix.
- **Level 2:** Isolate the problem → test one change → verify.
- **Level 3:** Form hypotheses → test systematically → identify the subsystem.
- **Level 4:** Use structured fault isolation at component, subsystem and system levels.

## Communication competency

- **Level 1:** Explain what was built.
- **Level 2:** Explain how it works.
- **Level 3:** Explain design decisions and test results.
- **Level 4:** Present requirements, architecture, evidence, limitations and improvements.

# 6. Documentation progression

| Level | Documentation |
|---|---|
| Level 1 | Student engineering notebook, simple circuit sketches, observations, project reflection |
| Level 2 | Engineering notebook, diagrams, measurements, test results, debugging notes |
| Level 3 | Requirements, system diagrams, schematics, code documentation, test records |
| Level 4 | Technical documentation, architecture, design decisions, validation evidence, project report |

The **engineering notebook** remains a continuous institute-wide practice.

# 7. Assessment progression

Assessment measures demonstrated capability rather than attendance or copying.

### Institute competency scale

1. **Guided** — can perform with substantial support.
2. **Developing** — can perform with some support.
3. **Capable** — can perform independently in familiar situations.
4. **Independent Maker** — can apply the skill independently, debug, improve and explain.

### Progression

**Level 1:** Can I build and explain it?

**Level 2:** Can I build, test, debug and modify it?

**Level 3:** Can I design and justify the system?

**Level 4:** Can I independently engineer, validate and communicate a complete solution?

---

# 8. Student independence progression

| Level | Student decisions |
|---|---|
| Level 1 | Component choice within a narrow set; simple improvements |
| Level 2 | Method, component and behavior choices within defined constraints |
| Level 3 | Architecture, components, implementation and testing approach |
| Level 4 | Requirements, architecture, technology choices, design trade-offs, validation strategy |

This is one of the primary indicators of progression between levels.

# 10. Course architecture rule

Every level/course should connect:

**Concept → Experiment → Project → Debugging → Explanation → Improvement → Evidence**

A course should not be treated as a collection of unrelated lessons.

Each course must contribute to the student's progression toward the next level.

---

# 11. Cross-level standards

The following should remain consistent across the institute:

- Learning philosophy
- Learn → Experiment → Build → Break → Debug → Understand → Improve → Create
- Project-based learning
- Engineering notebook
- Competency-based assessment
- Student portfolio
- Teacher methodology
- Safety culture
- Project documentation
- Project specification format
- Lesson-plan structure
- Assessment terminology
- Student progression records
- Version-controlled curriculum documentation

The complexity of these systems increases by level, but the underlying philosophy remains consistent.

---

# 12. Level transition requirements

Progression should not depend only on age.

A student moving to the next level should demonstrate an appropriate combination of:

- Core technical competencies
- Project evidence
- Debugging ability
- Engineering thinking
- Documentation
- Communication
- Independence
- Safety behavior

The detailed transition requirements should be defined as separate institute-wide progression standards before Level 2–4 programs are finalized.

# 14. Master rule for the four levels

The institute should move students through four fundamental questions:

### Level 1
**“What can I make happen?”**

### Level 2
**“How does what I built work?”**

### Level 3
**“How should I design this system?”**

### Level 4

This progression is the backbone of the ITS Education curriculum.
